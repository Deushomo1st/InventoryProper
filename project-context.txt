PROJECT STRUCTURE
================================================================================

16 standalone Spring Boot services in a single folder, each with its own
pom.xml. They share one Postgres database (inventory_deus) with one schema
per service. Cross-schema foreign keys are used (e.g., procurement.po_line.
sku_id REFERENCES catalog.sku.id). Services communicate via HTTP and share
a single JWT secret for authentication. No parent POM, no shared code at
compile time.

KEY DESIGN RULES (do not suggest violating these)
================================================================================

  - Passwords are never stored — only bcrypt hashes
  - The JWT secret is 256+ bits, shared across all services, never in
    source control
  - Permissions travel in JWT claims, not DB lookups on every request
  - Warehouse scoping is checked in every domain service, not the gateway
  - Every operational write records user_id from the JWT subject
  - 401 and 403 mean different things — never collapse them
  - The stock ledger is the only writer of quantity changes
  - Cross-schema FKs are enforced by Postgres
  - No tier may be started until the tier below it is demonstrable
    end-to-end
  - Eureka registration is not authentication — trust comes from JWT
    verification

# Context

I'm building a Spring Boot microservices inventory system. Tier 0 is done: an **ApiGateway** (port 9000) and an **AuthService** (port 9001). Frontend is plain HTML/CSS/JS — no framework, no build step. JWT auth, token stored in `sessionStorage` under keys `inv_jwt` and `inv_user`.

## Dual-access mode (critical — read first)

Every service must be runnable two ways, using the **same HTML files unchanged**:

- **Via the gateway** (`localhost:9000/ui/{service}/...`) — gateway handles login, downstream services trust the existing JWT.
- **Directly on its own port** (`localhost:9001/...`, `localhost:9002/...`, etc.) — each service handles its own login.

The mechanism that makes this work without conditionals:
- `sessionStorage` is per-origin, so gateway sessions (`localhost:9000`) and direct sessions (`localhost:9001`, etc.) are naturally isolated.
- All static paths in the HTML are absolute (`/js/app.js`, `/css/style.css`, `/login.html`). They resolve against whichever server is serving the page.
- `requireAuth()` redirecting to `/login.html` therefore does the right thing in both modes.

What this means for file layout:
- Each service has its own `static/login.html`, `static/js/app.js`, `static/css/style.css` — **intentional duplicates** of the gateway's copies, kept byte-identical.
- Each service exposes its UI pages under `static/ui/{service-name}/*.html`.
- The gateway routes `/ui/{service-name}/**` to the matching service.

## Relevant files

**Gateway** (`ApiGateway/src/main/resources/static/`):
- `login.html` — login form, POSTs to `/auth/login`, stores JWT in `sessionStorage`
- `menu.html` — 16-tile dashboard, pings `/health/{svc}`, links to `/ui/{service-name}/...`
- `css/style.css` — styles for login, `.menu-header`, `.tile-grid`, status dots. Light theme: `#3b82f6` primary, `#ef4444` for the logout button, `#f4f5f7` page background
- `js/app.js` — `getToken()`, `getUser()`, `logout()`, `apiFetch()`, `requireAuth()`

**Auth service** (`AuthService/src/main/resources/static/`):
- `ui/auth-service/index.html` — currently a meta-refresh to `users.html`
- `ui/auth-service/users.html` — user CRUD table hitting `/auth/users`
- `js/app.js`, `css/style.css` — duplicates of the gateway's copies (for direct-access mode; **do not delete**)
- *Missing:* `static/login.html` — needs to be added so direct access on `localhost:9001` works

## Problems

1. **`users.html` is a dead end.** No header, no "back to menu" link, no logout button, no user email. Once you click the Auth Service tile on `menu.html`, the only way back is editing the URL bar.
2. **No auth guard on `users.html`.** It calls `apiFetch('/auth/users')` directly. If the JWT is expired you get an alert popup over a blank table instead of bouncing to `/login.html` the way `menu.html` does via `requireAuth()`.
3. **No sub-nav inside the auth service.** When I add roles/permissions/warehouse-access pages they'll each be their own dead end with no way between them.
4. **Visual mismatch.** `users.html` uses `.container` / `.header` classes that aren't defined in `style.css`, so it looks unstyled next to `menu.html`.

## The fix I want

A reusable "app-shell" pattern. One function in `app.js`, called once at the top of each service page, that injects a consistent header with: back-to-menu link, breadcrumb (service / page), sub-nav tabs, user email, logout button. Also calls `requireAuth()` so unauthed visits bounce to login.

Sketch:

```js
function renderAppShell({ service, page, tabs = [] }) {
  requireAuth();
  document.body.insertAdjacentHTML('afterbegin', `
    <header class="app-shell">
      <a href="/menu.html" class="back">← Menu</a>
      <span class="crumb">${service} / ${page}</span>
      <nav class="sub-nav">${tabs.map(t => `<a href="${t.href}">${t.label}</a>`).join('')}</nav>
      <span class="user-email">${getUser()?.email ?? ''}</span>
      <button onclick="logout()">Log Out</button>
    </header>
  `);
}
```

Usage in `users.html`:

```js
renderAppShell({
  service: 'Auth Service',
  page: 'Users',
  tabs: [
    { href: '/ui/auth-service/users.html', label: 'Users' },
    { href: '/ui/auth-service/roles.html', label: 'Roles' },
    { href: '/ui/auth-service/permissions.html', label: 'Permissions' }
  ]
});
```

This shell works unchanged in both access modes because every path inside it is absolute. Via the gateway the `← Menu` link goes to the gateway's menu; in direct mode it goes to the service's own (which won't exist for a single-service direct run — that's fine, the link just 404s in that edge case).

## Constraints

- No frameworks, no build step. Plain HTML + CSS + JS only.
- All static paths absolute (`/js/...`, `/css/...`, `/ui/...`).
- `menu.html` already has its own header and should **not** call `renderAppShell` — the shell is only for inner service pages.
- The auth-service's `static/js/app.js` and `static/css/style.css` are intentional duplicates for direct-access mode. Keep them in sync with the gateway's copies; do not delete them.
- Every future service (catalog, inventory, etc.) will follow the same pattern: its own `login.html`, `js/app.js`, `css/style.css` mirroring the gateway, plus `ui/{service-name}/*.html` pages that each call `renderAppShell`.
